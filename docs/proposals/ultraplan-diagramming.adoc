= Ultraplan: assimilating the diagramming capability of Visual Paradigm and Flying Logic
:toc:
:toclevels: 3

== Purpose

The workbench already has a bowtie *page*: a three-column layout, a list of
threats and consequences, and buttons. It does not have a diagram *editor*. That
is the gap this plan closes.

Two mature products bracket what is needed:

* *Flying Logic* is the closest thing in existence to the workbench's reasoning
  core. It is a graph of causes and effects with AND/OR junctors, fuzzy
  confidence that propagates, groups that collapse, and a layout engine that
  takes full responsibility for arrangement so the thinker can keep thinking.
* *Visual Paradigm* is the reference for the *editor* around the model: model and
  view separated, a project browser, containers and layers, alignment guides,
  connector routing, traceability, and template-driven document generation.

The aim is not to clone either. It is to absorb what they establish as necessary
and refuse what would turn a risk workbench into a general CASE tool.

=== Scope discipline

[cols="1,2,4",options="header"]
|===
| Stance | Meaning | Example

| Adopt
| Absent today and required for credible use.
| Undo/redo, auto-layout, connector routing, keyboard editing.
| Adapt
| Present in another form; keep our semantics.
| Flying Logic's user-defined attributes become typed `fields` in BIM.
| Defer
| Valuable but not on the critical path; revisit with evidence.
| Full XMI fidelity, resource levelling, team server.
| Reject
| Would distort the product or the evidence model.
| 100+ notations; code round-trip; cloud-only collaboration; AI-generated risk
  claims without provenance.
|===

Effort is person-days for one experienced developer including tests and docs. It
is an estimate with real uncertainty, stated so that it can be argued with.

== Part 3 — What the fit map implies

Three architectural commitments follow from the Adopt rows.

=== 1. Model and view are separate

A `Node` in BIM may appear in several views (bowtie, causal chain, table,
outline, report). Deleting a shape must not delete a node; deleting a node must
warn about every view that shows it. This is VP-01 and it is the difference
between a drawing tool and a model tool.

=== 2. One layout engine, many entry points

Auto-layout is used by: first open, "tidy", incremental edit, animation between
states, export to a fixed canvas, and the minimap. It must therefore be
deterministic, incremental, and interruptible — not a batch script invoked once.

=== 3. The keyboard path is the primary path

The prototype's existing strength is that no drag, hover or gesture is required.
Every capability above must survive translation into keystrokes, and the canvas
must have a text-equivalent table view that is not a consolation prize. This is
also what makes the difference between a tool that disabled users can use and
one that claims to be accessible.

== Part 4 — Target architecture

=== 4.1 Layers

[cols="1,2,4",options="header"]
|===
| Layer | Owns | Rule

| Document
| BIM/1 semantics
| No geometry, no styling.
| Sheet
| Layout overlay per graph
| Discardable. Regenerable by layout.
| View
| Projection (bowtie, tree, table, outline, report)
| Read-only over the sheet; selects, never mutates semantics.
| Editor
| Selection, tools, commands, undo
| Every mutation is a command object.
| Renderer
| SVG scene
| No business rules.
|===

=== 4.2 Scene and hit-testing

* `SceneNode` tree mirroring groups; each view node carries `modelId` and a
  geometry box.
* Spatial index (uniform grid at small scale, R-tree above ~2k elements) for
  hit-testing and marquee selection.
* Z-order by layer, then by group depth, then explicit index.
* Hit-test priority: ports, edge, node body, group, background — with a
  configurable tolerance in CSS pixels, not model units.

=== 4.3 Commands and undo

[source,text]
----
Command = { id, label, apply(state) -> Patch, invert(Patch) -> Patch }
----

* All mutations flow through `dispatch(command)`.
* Drags coalesce into one command with a transaction id.
* Imports are one command (all or nothing at commit).
* Undo stack keeps patches plus periodic snapshots for bounded memory; a
  checkpoint is a named marker in the same stack.
* Undo is per-user and per-session; the document's `revisions` list is the
  durable history. Do not confuse the two.

=== 4.4 Layout engine

* *Cycle breaking* by DFS with a feedback-edge preference (BIM already requires
  feedback edges to carry a lag, which gives the breaker a signal).
* *Layering*: longest-path, then tighten with a network simplex pass for
  compactness.
* *Ordering*: median/barycenter with a transpose pass to reduce crossings.
* *Coordinates*: Brandes–Köpf for straightness with balanced aspect ratio; node
  size variation handled as port constraints.
* *Bowtie specialisation*: a two-wing constraint — prevention wing upstream of
  the top event, mitigation downstream — so the canonical shape emerges rather
  than being imposed.
* *Incremental mode*: pin user-positioned nodes, reflow the rest, minimise
  displacement; animate the delta.
* *Determinism*: same input, same output, byte-for-byte in the layout overlay.
  This is testable and makes golden files possible.

Quality metrics, measured on every change and in CI benchmarks: edge crossings,
edge bends, total edge length, node overlap (must be zero), label overlap, aspect
ratio, and displacement from the previous layout.

=== 4.5 Routing and labels

* Orthogonal A* around node obstacles with a cost for bends and shared runs.
* Straight lines for short hops; curved only where it aids reading.
* Port assignment by angle to reduce crossings; ports snap to a grid of 3 per
  side by default.
* Label placement: candidate positions scored for overlap and distance; labels
  move with the edge and stay horizontal regardless of edge direction.
* Shared dependencies render as a distinct run with a label, never as two
  coincident lines.

=== 4.6 Notation packs and method packs

A notation pack is data:

[source,json]
----
{
  "id": "bowtie",
  "version": "1.0.0",
  "kinds": {
    "hazard":    { "shape": "hexagon",  "ports": "auto", "size": [160, 88] },
    "top-event": { "shape": "circle",   "ports": "auto", "size": [200, 200] },
    "barrier":   { "shape": "barrier",  "ports": ["in", "out"], "size": [180, 72] }
  },
  "constraints": [
    { "rule": "barrier.mustLinkToPath", "message": "A control must act on a threat or consequence." }
  ],
  "layout": { "orientation": "left-to-right", "engine": "layered+bowtie" },
  "palette": ["hazard", "top-event", "threat", "consequence", "barrier", "escalation"]
}
----

A method pack adds vocabulary, invariants, defaults, report templates and a
review checklist (for example the Categories of Legitimate Reservation). This is
how Flying Logic's domains and Visual Paradigm's profiles both collapse into one
mechanism.

=== 4.7 Interaction

* Pointer and keyboard are peers. Every pointer gesture has a command and a
  shortcut; every shortcut is discoverable from a command palette.
* Modes: select, connect, annotate. Modal tools are visible and dismissible,
  never silent.
* Drop zones (FL-14) for insertion; keyboard insertion via "insert before /
  after / child" commands.
* In-canvas editing with IME safety: composition events must not commit a node
  rename on every keystroke.
* Drag threshold and cancel; no action on hover alone.

=== 4.8 Accessibility as a spec, not an aspiration

* Target WCAG 2.2 AA, as the README already states for the prototype.
* Focus model: roving tabindex across nodes in reading order, edge focus via a
  dedicated mode, group focus with expansion.
* The accessible tree mirrors the graph: groups as groups, edges as a list under
  their source with "connects to" text.
* Live regions announce structural changes ("Control added after Threat 3").
* Every diagram has a table equivalent generated from the same projection; the
  table is editable where the canvas is.
* Colour never carries meaning alone: gates, confidence, and barrier status all
  have text or symbol equivalents.
* Motion: respect reduced-motion; layout changes become instant with an optional
  summary announcement.

=== 4.9 Rendering and export

* SVG is the primary renderer: selectable text, printable, accessible, and
  diffable. A canvas fallback is permitted above ~5k elements with an SVG/table
  export path preserved.
* Self-contained SVG export embeds fonts as outlines or subset WOFF, and embeds
  symbol images as data URIs.
* PNG, PDF generated from the same scene, so what is exported is what is seen.
* DOT export for analysis; a "layout debug" export for support.

=== 4.10 Collaboration, diff and merge

* Local-first. A document is a file.
* Revision comparison is a BIM diff (semantic), rendered as a change list plus a
  highlighted diagram — this is VP-23's impact analysis applied to time.
* Three-way merge at the node and edge level, with conflicts presented as
  choices, never auto-resolved for semantics.
* CRDT or server sync is deliberately out of scope until a requirement exists;
  the IR makes it possible later without redesign.

== Part 7 — Evaluation

Ship criteria are behavioural, not feature-count:

. A facilitator can build a five-threat, three-consequence bowtie with two
  controls, on a laptop, using only the keyboard, in under ten minutes.
. A practitioner can lay out a 40-node TOC tree and get a readable diagram
  without manual positioning.
. Every diagram has a table equivalent that a screen-reader user can edit.
. Layout is deterministic; the same document opens identically on two machines.
. A 1,000-node imported register is navigable and searchable within the
  performance budgets.
. Export to SVG, PDF, DOT and AsciiDoc from one command path, with no visual
  surprises.
